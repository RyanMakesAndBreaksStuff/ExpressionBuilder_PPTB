# Feature 021: Codebase Pattern Exploration in sdd-init

**Status:** Approved
**Created:** 2026-07-04
**Branch:** `021-codebase-pattern-rules-init`

---

## Problem Statement

`sdd-init`'s rules generation phase (spec 019) dispatches three web-research subagents that produce rules based on community best practices for the detected tech stack. These rules describe what the stack's ecosystem recommends, not what the project actually does. When `sdd-init` is invoked on a project that already has code — a team adopting SDD mid-project, or a project seeded with existing scaffolding — the actual naming conventions, architectural patterns, test structure, and error handling conventions already in use are invisible to the init flow. Rules that conflict with existing code are immediately stale; rules that duplicate existing patterns add noise.

## Goals

- Extend the rules generation phase with codebase exploration subagents that read actual source files and synthesize rules from observed patterns
- Run codebase exploration subagents in parallel with the existing web-research subagents so init time does not increase
- Merge codebase-derived findings into the same rule file proposals the user reviews — codebase evidence enriches or overrides generic web-research rules where they conflict
- Gracefully skip codebase exploration when the project has no source files yet (new empty project)

## Non-Goals

- Replacing the web-research subagents (spec 019) — both sources run; findings are merged
- Exhaustive full-codebase indexing — exploration uses sampling (bounded file counts per area)
- Generating rules for projects that already have `.claude/rules/` (not init territory)
- Standalone `sdd-rules-update` skill that re-runs exploration post-init
- Analyzing binary files, build artifacts, or dependency source code
- Producing architecture diagrams or documentation beyond rule file content

## Users and Context

**Primary users:** Claude (the AI model) — reads the updated `sdd-init` skill prose and drives the codebase exploration subagents  
**Secondary users:** SDD practitioners — invoke `sdd-init` on a project that already has code and receive rules that reflect their actual conventions  
**Usage context:** Any `sdd-init` invocation on a project with existing source files  
**User mental model:** Rules generated by init should describe what we actually do, not just what the internet says we should do

---

## User Stories

### Story 1: Codebase exploration runs in parallel with web research

**As a** developer initializing an existing project with SDD  
**I want** codebase exploration to happen without slowing init down  
**So that** the total init time stays comparable to init without exploration

**Acceptance criteria:**

- [ ] **AC-1.1** Given `sdd-init` reaches Step 4.2 and source files exist When subagents are dispatched Then the codebase exploration subagents are dispatched concurrently alongside the three web-research subagents — not sequentially after them
- [ ] **AC-1.2** Given `sdd-init` reaches Step 4.2 and no source files exist (new empty project) When subagents are dispatched Then only the three web-research subagents are dispatched; no codebase exploration subagents are launched and the user is not notified
- [ ] **AC-1.3** Given codebase exploration subagents are dispatched When the controller collects results Then it waits for all subagents (exploration + web research) to complete before proceeding to Step 4.3

### Story 2: Exploration subagents sample the codebase within bounded scope

**As a** developer  
**I want** exploration to be fast and focused, not a full indexing crawl  
**So that** init completes in a reasonable time even on large codebases

**Acceptance criteria:**

- [ ] **AC-2.1** Given a project with source files When an exploration subagent is dispatched Then it reads at most 10 source files per top-level directory, prioritizing files in `src/`, `lib/`, `app/`, or equivalent primary source directories
- [ ] **AC-2.2** Given source and test files exist When exploration subagents are dispatched Then one subagent is dedicated to source file patterns and a separate subagent is dedicated to test file patterns — they do not share file scope
- [ ] **AC-2.3** Given a project with more files than the sampling limit When an exploration subagent reads files Then it prefers files at the root of each directory over nested files, so the most representative patterns are sampled first

### Story 3: Source pattern subagent derives naming and structural conventions from code

**As a** developer  
**I want** rules for naming, structure, and architectural patterns to reflect what's actually in my codebase  
**So that** the generated rules describe real conventions, not hypothetical ones

**Acceptance criteria:**

- [ ] **AC-3.1** Given sampled source files When the source pattern subagent synthesizes findings Then it reports: file naming convention (kebab-case / PascalCase / snake_case), function naming convention, variable naming convention, and module/import organization pattern
- [ ] **AC-3.2** Given sampled source files When the source pattern subagent synthesizes findings Then it reports: observed architectural patterns (e.g. service layer, repository pattern, MVC structure) derived from directory names and import graphs
- [ ] **AC-3.3** Given sampled source files When the source pattern subagent synthesizes findings Then it reports: error handling patterns (e.g. exception vs. result type, centralized error handler) observed from function bodies
- [ ] **AC-3.4** Given fewer than 3 source files exist When the source pattern subagent runs Then it reports "insufficient files for reliable pattern detection" and returns an empty findings object — init does not fail

### Story 4: Test pattern subagent derives test structure and assertion conventions from test files

**As a** developer  
**I want** rules for test organization and assertion style to match what my test files already show  
**So that** new tests generated by SDD skills are consistent with existing ones

**Acceptance criteria:**

- [ ] **AC-4.1** Given sampled test files When the test pattern subagent synthesizes findings Then it reports: test file naming convention (e.g. `*.test.ts`, `*_test.go`, `test_*.py`), test organization (describe/it blocks, test suites, flat functions), and assertion style (expect/assert/should)
- [ ] **AC-4.2** Given sampled test files When the test pattern subagent synthesizes findings Then it reports: mock and fixture patterns (e.g. factory functions, fixture files, inline setup)
- [ ] **AC-4.3** Given no test files exist When the test pattern subagent runs Then it reports "no test files found" and returns an empty findings object — init does not fail

### Story 5: Codebase findings enrich rule file proposals

**As a** developer  
**I want** rule files to cite concrete examples from my own codebase  
**So that** the rules are immediately recognizable and actionable for my team

**Acceptance criteria:**

- [ ] **AC-5.1** Given codebase exploration returned findings When rule file proposals are assembled Then each finding that overlaps with a web-research rule is merged: the rule retains the web-research rationale and gains a codebase example (e.g. "✓ `getUserById` — observed in `src/users/service.ts`")
- [ ] **AC-5.2** Given a codebase pattern contradicts a web-research rule When the rule file proposal is assembled Then the codebase pattern is used as the rule and the web-research recommendation is appended as a `Note:` comment (e.g. "Note: web research recommends X — confirm this matches your intent")
- [ ] **AC-5.3** Given codebase exploration returned findings and web research returned no results for a topic When rule file proposals are assembled Then codebase-derived findings alone are used to propose that rule file
- [ ] **AC-5.4** Given both exploration and web research returned empty results for a topic When rule file proposals are assembled Then no rule file is proposed for that topic

### Story 6: User can distinguish codebase-derived rules from web-research rules

**As a** developer reviewing proposed rule files  
**I want** to know which rules are grounded in my actual code vs. external recommendations  
**So that** I can prioritize approving rules that match what we already do

**Acceptance criteria:**

- [ ] **AC-6.1** Given a rule was derived solely from codebase exploration When the rule line is written Then it is prefixed with `[observed]` to distinguish it from web-research rules
- [ ] **AC-6.2** Given a rule was derived from both codebase and web research When the rule line is written Then it carries no prefix — the merged rule is presented as a single confident recommendation
- [ ] **AC-6.3** Given a rule was derived solely from web research When the rule line is written Then it carries no prefix — existing behavior from spec 019 is unchanged

## Functional Requirements

- **FR-1** Codebase exploration is triggered at Step 4.2 when the project has at least one source file outside of `node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `target/`
- **FR-2** Exactly two codebase exploration subagents are dispatched: Source Pattern Subagent and Test Pattern Subagent
- **FR-3** Both exploration subagents run concurrently with the three web-research subagents (all five dispatched in the same parallel batch)
- **FR-4** Each exploration subagent reads at most 10 source files per top-level directory; total file reads per subagent are bounded at 30
- **FR-5** Excluded paths for exploration: `node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `target/`, `coverage/`, `__pycache__/`, `*.min.js`, `*.d.ts`
- **FR-6** Source Pattern Subagent reports: file naming convention, function naming convention, variable naming convention, import/module organization, observed architectural patterns, error handling patterns, and enforced conventions detected from configuration files (`.eslintrc`, `.eslintrc.json`, `.eslintrc.js`, `.prettierrc`, `tsconfig.json`, `pyproject.toml` tool sections, `.rubocop.yml`, and equivalents)
- **FR-7** Test Pattern Subagent reports: test file naming convention, test organization style, assertion style, mock/fixture patterns
- **FR-8** Exploration subagent results are structured summaries — not raw file content — consumable by the controller without further file reads
- **FR-9** Where a codebase pattern and a web-research rule overlap, the merged rule includes a codebase example reference
- **FR-10** Where a codebase pattern contradicts a web-research rule, the codebase pattern is used as the rule; the web-research recommendation is preserved as a `Note:` comment (e.g. "Note: web research recommends X — confirm this matches your intent")
- **FR-11** Rules derived solely from codebase exploration are prefixed with `[observed]` in the proposed rule file
- **FR-12** Empty or insufficient codebase exploration results do not fail init — the controller falls back to web-research results only for affected topics

## Non-Functional Requirements

- **NFR-1** All five subagents (3 web-research + 2 exploration) run concurrently in a single parallel batch — no sequential staggering
- **NFR-2** Each exploration subagent completes in under 60 seconds on a codebase up to 500 source files (due to sampling bound of 30 files per subagent)
- **NFR-3** Exploration subagent results are structured objects (not prose) so the controller can merge them with web-research results programmatically
- **NFR-4** Codebase exploration does not alter any project files — it is read-only

---

## Error Scenarios

- **No source files found**: Skip both exploration subagents silently; init continues with web-research rules only
- **Source Pattern Subagent returns insufficient files** (< 3): Mark source pattern findings as empty; init continues with web-research only for source convention rules
- **Test Pattern Subagent finds no test files**: Mark test pattern findings as empty; init continues with web-research only for test convention rules
- **Exploration subagent times out**: Treat as empty result; log "codebase exploration timed out — using web research results only"; init does not fail
- **Exploration finds contradictions in multiple rule topics**: Each contradiction is surfaced independently as a `Note:` comment in its respective proposed rule file

## Out of Scope

- Re-running codebase exploration on an already-initialized project
- A standalone skill for updating rules from codebase patterns post-init
- Full codebase indexing without sampling bounds
- Exploration of binary files, build artifacts, or dependency source
- Generating architecture diagrams or relationship maps
